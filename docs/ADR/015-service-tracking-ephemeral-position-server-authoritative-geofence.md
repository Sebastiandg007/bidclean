# ADR-015: Service Tracking — Ephemeral Live Position, Server-Authoritative Geofence over a Creation-Time Snapshot, Backend-on-the-Path Ingress (Option A), and a Fan-Out Outbox with Per-Consumer Checkpoints

## Status
Accepted

## Context
After a match is locked and escrow is charged, the Cleaner heads to the property while the Host watches the live position approach, and a geofence must confirm physical arrival to unlock on-arrival video verification (Spec 17, `service-tracking`, first of Sprint 5). This must NOT introduce a new participant, authorization, or payment model — a session is a lifecycle bound 1:1 to a matched offer, inheriting the offer's two parties exactly as chat/voip inherit authorization from a conversation. Three concerns had no implementation yet: (1) how position gets from the Cleaner to the geofence and to the Host, (2) how arrival is decided in a way downstream specs can trust, and (3) how the durable `service_*` events fan out to multiple independent consumers (Spec 16 notifications, Spec 18 video) without one starving the other. Critically, the offer/escrow path did not yet emit a single durable "activation" fact — service-tracking would otherwise have to query `offer.status` and `payment.status` separately, coupling two bounded contexts.

## Decision
1. **Live position is ephemeral — never persisted as a trail.** Position samples are evaluated server-side and re-published best-effort to the Host over Centrifugo; PostgreSQL never holds a breadcrumb/route history. The **only** durable location-derived datum is the scalar `arrival_distance_m` at the geofence crossing. Coordinates are never logged verbatim.
2. **The backend is on the path (Option A) — control-plane / media-plane split.** The Cleaner does NOT publish to Centrifugo. Position is POSTed to `POST /service-sessions/:id/position`; the server rate-limits per `(user, session)`, gates eligibility (accuracy + staleness + clock-skew), runs the PostGIS geofence, transitions durably if arrived, then re-publishes the position to `service:session:{id}` for the Host. The channel is an **output** transport (server → Host); the Host is a read-only subscriber and the Cleaner is not a channel publisher at all.
3. **Server-authoritative geofence over a creation-time snapshot, with an explicit GPS threat model.** Arrival is decided by the server via `ST_DWithin` between the reported point and the session's `property_location_snapshot` (captured at creation) within the snapshotted `geofence_radius_m`, so a config change or a mid-session property deletion never retroactively alters an in-flight session. `accuracy` is an **eligibility gate only** (never a radius correction); `arrival_distance_m` is the geometric geodesic distance. The server owns the *computation*, but reported coordinates are client telemetry, NOT cryptographic proof of physical presence — anti-spoofing is explicitly out of scope (human presence is complemented by Spec 18's on-arrival video).
4. **One durable activation fact triggers creation — never two cross-context queries.** The offer/escrow path emits a single `service_activation_ready` outbox row (offer `MATCHED` AND escrow `CAPTURED`) in the SAME transaction as the escrow HELD transition. service-tracking reacts to that one fact and creates the session idempotently (`UNIQUE offer_id`).
5. **The `service_outbox` is a fan-out source with NO shared `relayed_at`.** Each downstream consumer drains events lacking its own `(event_id, consumer_name)` ack row in `service_outbox_consumers` (`NOT EXISTS`) and acks only its own pair, so the notifications consumer acking `service_arrived` can never starve the video consumer. service-tracking, in turn, consumes the upstream `service_activation_ready` via its OWN `service_activation_consumed` cursor rather than mutating a shared marker on a table it does not own.

## Reasoning
- **Ephemeral position is a privacy + simplicity decision.** A persistent location history would be a standing privacy liability and adds no MVP value; the backend evaluates + relays, Mapbox only renders. If a persistent route log is ever needed, it gets its own spec with its own privacy review.
- **Option A makes the server unambiguously the geofence authority.** Because every sample it acts on passes through the API, the arrival decision, its server timestamp, and `arrival_distance_m` are the durable facts — a client "arrived" claim is advisory only. It also keeps the Host's view flowing without granting the Cleaner any publish scope.
- **A creation-time snapshot decouples the geofence from the live property row.** Deletion coherence (Spec 13) keeps `property_id` `ON DELETE SET NULL`, but the geofence depends on the snapshot, so a mid-session property deletion does not break arrival evaluation — only an unusable snapshot would (which the `NOT NULL` schema prevents in normal operation).
- **A single durable fact avoids coupling.** Consuming one `service_activation_ready` event is the same additive, non-blocking outbox discipline established by push-notifications (Spec 16): a tracking-side failure never rolls back or blocks the match/escrow, and the row stays re-drainable via the consumer's own checkpoint.
- **Per-consumer checkpoints are required for correct fan-out.** A single shared `relayed_at` would be a data race: whichever consumer flipped it first would starve the other of `service_arrived` — the very event that unlocks Spec 18. Keying acks by `(event_id, consumer_name)` makes delivery at-least-once and idempotent PER consumer, independent of every other consumer.
- **Single-winner state machine.** Every advancing/terminal transition is `UPDATE ... WHERE id=:id AND state=:expected` and, in the SAME transaction, sets the derived timestamps AND writes the `service_outbox` event, so history can never observe an `ARRIVED` session without `arrived_at`, nor a `service_arrived` event without a committed arrival.

## Position, Geofence & Fan-Out Flow
1. Offer/escrow commits the match + escrow capture and writes `service_activation_ready` (`event_id = service_activation_ready:<offerId>`, payload `{ offerId, hostId, cleanerId, propertyId }`) into `service_activation_outbox` in the same tx.
2. `ServiceActivationConsumer` drains rows it has not yet acked (`NOT EXISTS` vs `service_activation_consumed`), calls `createFromActivation` (snapshots the property point + radius, `ON CONFLICT (offer_id) DO NOTHING`), then records its own ack.
3. Cleaner POSTs `en-route` (`MATCHED → EN_ROUTE`, `service_en_route`), then position samples. The server rate-limits, gates eligibility, runs `ST_DWithin` over the snapshot; an eligible in-radius sample drives a single-winner `EN_ROUTE → ARRIVED` (server timestamp + `arrival_distance_m` + `service_arrived`, one tx). Every sample is best-effort re-published to the Host.
4. Cleaner POSTs `start` (`ARRIVED → IN_PROGRESS`, `service_started`) — the hand-off to Specs 18/19/20.
5. The notifications (Spec 16) and video (Spec 18) consumers each drain `service_outbox` via their own `(event_id, consumer_name)` checkpoint; a bounded, idempotent sweep force-expires stale/abandoned sessions with a differentiated `ended_reason`.

## Alternatives Considered
- **Client publishes position directly to Centrifugo (Option B).** The server would not see every sample it acts on; the geofence authority would be ambiguous and the channel would need a Cleaner publish grant. Rejected in favor of Option A.
- **Persist a breadcrumb/route history.** A standing privacy liability with no MVP value; rejected in favor of ephemeral relay + the single `arrival_distance_m` scalar.
- **Correct the geofence radius by reported accuracy.** Error-bounded distance is more complex and easy to get subtly wrong; `accuracy` as a pure eligibility gate is a documented MVP simplification. Rejected for MVP.
- **Reuse `payment_outbox` for `service_activation_ready`.** The notifications relay marks every `payment_outbox` row relayed even for a type its mapper does not handle, silently dropping the fact for any other consumer. Rejected in favor of a dedicated `service_activation_outbox` table.
- **A single shared `relayed_at` on `service_outbox`.** A fan-out data race that starves one consumer. Rejected in favor of per-consumer `service_outbox_consumers`.
- **service-tracking querying `offer.status` AND `payment.status` separately.** Couples two bounded contexts and is not atomic. Rejected in favor of one durable `service_activation_ready` fact.

## Consequences
- The offer/escrow path gains one additive, read-only responsibility: emitting `service_activation_ready` in the escrow HELD transaction (the escrow `findOfferRates` read was extended by one column, `property_id`, to carry the geofence property). No offer/negotiation/escrow contract changed beyond this and the existing offer-terminal force-cancel.
- The mobile client needs foreground location permission for the Cleaner; denial degrades gracefully (the session still works via the server-side geofence on whatever coordinates are provided). Mapbox renders position/destination only — never a source of truth.
- The `service:session:{id}` channel token is minted by auth (reusing `CENTRIFUGO_TOKEN_SECRET`) only after the participation rule passes, scoping the Host to read-only with no publish grant.
- A terminal-for-tracking session is an immutable audit fact (no `deleted_at`); `host_id`/`cleaner_id`/`property_id` are `ON DELETE SET NULL`, only `offer_id` CASCADEs — no user-cascade path.
- Push delivery/OS wake-up (Spec 16), on-arrival video (Spec 18), checklist/photos (Spec 19), completion + escrow release (Spec 20), SOS/panic, and in-app turn-by-turn navigation are all out of scope; service-tracking only emits durable `service_*` facts and hands off at `IN_PROGRESS`.
