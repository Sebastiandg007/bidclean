### Added
- **Account deletion now cleans up the subscription mirror + ledger (Spec 11 ↔ user-profile integration)** — added a `CLEANUP_SUBSCRIPTION_MIRROR` step to the `DeletionJobProcessor` cascade (`services/api/src/profile/account/deletion-job.processor.ts`), running after subscription cancellation and before the Keycloak delete. The step hard-deletes the disposable per-user mirror row (`DELETE FROM subscriptions`) and anonymizes the append-only ledger (`UPDATE subscription_events SET user_id = NULL`) in one transaction, so audit history survives deletion while PII/read-model state is removed. It is idempotent (missing mirror / already-anonymized ledger is a no-op), never blocks on RevenueCat, and is safe to retry. Added the new step name to `DeletionStep` (`account.types.ts`) for audit logging and extended the PII-anonymization test to assert the mirror-cleanup and PII transactions independently of ordering. Verification: `services/api` ESLint clean and TypeScript diagnostics clean on the touched files.

The token is no longer provided or exported by `commission` — it is bound and exported by `subscriptions`, and only consumed internally by `CommissionRatesProvider`, so downstream consumers of `CommissionModule` (`offers`, `negotiation`) still resolve `COMMISSION_RATES` with no circular dependency (coupling stays one-directional: Commission → Subscriptions via the contract token). Registered `SubscriptionsModule` in `app.module.ts` ahead of `CommissionModule`. From now on a Cleaner/Host PRO entitlement resolves the reduced, per-role commission rate through the live mirror rather than always FREE. - **Subscriptions — reconciliation backstop sweep (Spec 11 — revenuecat-subscriptions)** — implemented `services/api/src/subscriptions/reconciliation/subscription-reconciliation.service.ts`, the periodic `@Interval` sweep that keeps the mirror consistent with RevenueCat truth independent of webhook delivery. Each sweep runs two passes: **converge** stale/never-reconciled rows (`findStaleForReconciliation`) against the authoritative subscriber snapshot (idempotent no-op when already correct, P6), then **discover** known subscribers with no mirror row yet (a missed webhook) via the new `SubscriptionsRepository.findLedgerUserIdsWithoutMirror` ledger query and create them from RevenueCat truth (P18). A RevenueCat outage (null snapshot) leaves the affected row untouched and retries next interval, and any repository/sweep failure is logged without throwing so the schedule keeps running (P8). Added `findLedgerUserIdsWithoutMirror` to the repository and unit tests (`__tests__/subscription-reconciliation.service.spec.ts`, 5 tests) covering converge, no-op-when-correct, discovery, outage-safety, and query-failure resilience. No `docs/ARCHITECTURE.md` change required — the `Subscriptions Module` node and its `RevenueCat API` edge already exist; this is an internal component below diagram granularity.

Added `subscription-dispatch.worker.ts` (recovery: re-enqueues aged `RECEIVED`/`QUEUED` rows not yet processed) and the supporting `SubscriptionsRepository.findLedgerRow`. - **Subscriptions — RevenueCat webhook controller (Spec 11 — revenuecat-subscriptions)** — implemented `services/api/src/subscriptions/webhooks/revenuecat-webhook.controller.ts`, the public `POST /webhooks/revenuecat` ingress (not under the JWT guard). It authenticates each request from the preserved raw body via `verifyWebhook` (HMAC-SHA256 preferred, shared-secret bearer fallback, replay tolerance) and rejects failures with 401 and no mutation, then sanitizes the event, deduplicates by `revenuecatEventId`, and commits a `RECEIVED` ledger row *before* acknowledging so an ACKed event is never lost (P16). Processing is enqueued on the BullMQ subscription queue (marking `QUEUED`) best-effort — an enqueue failure leaves the `RECEIVED` row for the dispatch recovery worker rather than failing the ACK — and the handler always returns a fast `{ received: true }`. A concurrent redelivery that loses the insert race is treated as already received. Updated `services/api/src/subscriptions/README.md` to mark `webhooks/revenuecat-webhook.controller.ts` Implemented. - **Subscriptions — RevenueCat ingestion primitives (Spec 11 — revenuecat-subscriptions)** — implemented the pure, side-effect-free building blocks under `services/api/src/subscriptions/revenuecat/`: `revenuecat.constants.ts` (logical→configured entitlement id map + `toEntitlementKeys()`), `revenuecat-signature.ts` (HMAC-SHA256 verify with timestamp tolerance + constant-time compare), `revenuecat-payload.sanitizer.ts` (whitelist safe fields only, no PII/secrets), and `revenuecat-event.mapper.ts` (maps a sanitized RevenueCat event to the per-entitlement `EntitlementDelta[]` it implies). - **Commission System spec complete (Spec 10 — commission-system)** — all implementation tasks (including optional `*` tasks) finished and verified. A new backend-only `commission` NestJS module resolves **which commission rate applies** to each side of a service and records who changed the rules, without ever computing cents, moving money, owning subscriptions, or serving analytics.
  - **Two-moment resolution** (ADR-006): the Host service fee is resolved at **offer creation** (via `COMMISSION_RATES.resolveHostRate`, consumed by `offer-publishing` and fed into its own `CommissionService`) and the Cleaner commission is resolved at **match** (via `resolveCleanerRate`, consumed by `offer-negotiation` for the winning Cleaner and snapshotted onto the winning proposal/offer). Each rate is immutable once snapshotted; a later rule change never re-prices an existing offer (P11).
  - **No circular dependency:** the module does NOT import `OffersModule` or `CommissionService` — coupling is one-directional via the `COMMISSION_RATES` token (no `forwardRef`). Cents arithmetic stays in each consumer's own `CommissionService` (P7).
  - **Versioned scoped rules:** one rule sets one side (`applies_to` HOST|CLEANER, single `rate_bps`), scoped by country (ISO alpha-2 or ANY), subscriber tier (FREE/PRO/ANY), and optional service type. Winner ordering is deterministic — specificity → priority → `effective_from` → lowest UUID (P2/P3). Effective windows are half-open `[from, to)`; future-dated rules are inert until their window opens (P8, scheduled changes without a deploy). An empty ruleset reproduces the exact prior flat behavior (P4).
  - **Overlap safety:** a PostgreSQL GiST `EXCLUDE` constraint (over the scope tuple + `tstzrange`) prevents two active rules with identical scope and overlapping windows even under concurrent writes; the repository maps the violation to a 409.
  - **Audit & retention:** every rule create/update/activate/deactivate appends one immutable `commission_rule_audit` row (actor, timestamp, before/after) in the same transaction as the write (P10); rules are never physically deleted (audit FK `ON DELETE RESTRICT`).
  - **Safe degradation:** subscriber tier is obtained only via the `SUBSCRIPTION_TIER` contract (a FREE-returning stub until `revenuecat-subscriptions`, Spec 11), bounded by a timeout; on any failure resolution degrades to the environment default rate and never blocks creation or match (P6).
  - **PRO discount:** a Cleaner PRO pays the reduced, most-specific matching rate resolved at match; Host and Cleaner sides resolve independently, so one matched offer can combine a FREE Host fee with a PRO Cleaner commission (P9).
  - **Per-role tier resolution:** subscriber tier is now resolved per role rather than globally. Added `SubscriberRole` (HOST/CLEANER) and `SUBSCRIPTION_TIER.getRoleTier(userId, role)`; the provider maps each rate side to its role (`roleForSide`) so the Host fee derives from `host_pro` and the Cleaner commission from `cleaner_pro` independently — a user who is PRO in one role and FREE in the other resolves correctly on each side (P9). `getTier` is retained as the global (PRO-in-any-role) answer for non-role-scoped consumers.
  - **Distributed cache:** the active ruleset is cached in memory and invalidated across API instances via Redis pub/sub on every write, with a TTL refresh backstop; a refresh failure keeps the last-good snapshot (never silently drops to env defaults).
  - **Operator admin surface:** `/admin/commission/rules` CRUD guarded by JWT + an operator allowlist (`COMMISSION_ADMIN_KEYCLOAK_IDS`) + a per-operator Redis rate limit; business-policy per-side rate caps reject absurd rates (400), distinct from the technical `[0,10000]` bound.
  - **Schema:** migrations `1700000015000-CreateCommissionRules` (requires `btree_gist`) and `1700000016000-CreateCommissionRuleAudit`, both reversible.
  - **Verification:** `services/api` typecheck clean, ESLint `--max-warnings 0` clean, full suite 111 suites / 1277 tests pass (commission module alone: 7 suites / 51 tests — unit + fast-check properties P1–P11 + scenarios 16.1–16.7); `packages/shared` typecheck clean. ### Fixed
- **Stripe Escrow — reconciliation hardening (Spec 9 — stripe-escrow)** — closed the two robustness gaps flagged in the audit, both fully inside this spec (no dependency on `dispute-system`):
  - **Dispute webhook backstop:** `PaymentReconciliationService` now runs a second sweep (`reconcileDisputes`) that lists Stripe disputes per charge for payments with `dispute_status = NONE` (catches a missed `charge.dispute.created`, pausing auto-release, P5) and `dispute_status = OPEN` (catches a missed `charge.dispute.closed`, resolving won/lost). Previously the dispute lifecycle was webhook-only with no backstop. Added `StripeClient.listDisputesForCharge` and `PaymentsRepository.findChargedPaymentsForDisputeCheck` (joins the SUCCEEDED attempt's charge id). The formal evidence workflow stays owned by the future `dispute-system` spec — this only converges status.
  - **Non-terminal charge intents:** `reconcilePayment` now explicitly recognizes `requires_action` / `requires_confirmation` / `processing` and leaves the payment in `PROCESSING` with a warning log (so aged rows surface for alerting) instead of silently doing nothing; only `canceled` / `requires_payment_method` move a payment to `FAILED`.
  - Verified: typecheck + ESLint clean, 18 payments suites / 120 tests pass.

- **Stripe Escrow — post-implementation audit fixes (Spec 9 — stripe-escrow)** — resolved money-safety and correctness findings from a behavioral review:
  - **Stranded-charge recovery (P11):** the charge attempt's real Stripe PaymentIntent id is now persisted immediately after `createPaymentIntent` (via new `PaymentsRepository.recordAttemptIntentId`) and again on success in `markChargeSucceeded`, replacing the `pending:` placeholder. `PaymentReconciliationService` now falls back to `StripeClient.findPaymentIntentByPaymentId` (Stripe search by `metadata.paymentId`) to heal a payment left `PROCESSING` after a crash between the charge call and the DB write — previously such a payment was permanently unrecoverable.
  - **Stripe fee captured on charge:** the charge PaymentIntent is created with `expand: ['latest_charge.balance_transaction']` so `stripe_fee_cents` and `net_platform_revenue_cents` are recorded correctly at capture instead of defaulting to 0.
  - **Refund net-revenue guard:** `applyRefund` now rejects negative amounts and any `reversal > refund` at the repository boundary (prevents net revenue from drifting upward on a malformed refund) and documents that the Stripe fee stays absorbed from capture.
  - **Dispute resolution:** `charge.dispute.closed` now maps only explicit `won`/`lost` outcomes; non-terminal statuses (e.g. `warning_closed`) no longer count as a loss.
  - **Idempotent release:** `markReleased` treats an already-released payment as a clean no-op under concurrent triggers instead of throwing a conflict (P4).
  - Verified: `services/api` typecheck clean, ESLint clean, 18 payments suites / 114 tests pass.
