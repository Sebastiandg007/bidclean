# Implementation Plan: Dispute System

## Overview

`dispute-system` (Spec 21, the first of Sprint 6 — Polish & Extras) owns the "the job didn't go right" case: a Host (or, in defined cases, a Cleaner) raises a dispute, evidence is gathered from the durable facts the service already produced, and a resolution — `FAVOR_CLEANER`, `FAVOR_HOST`, or `PARTIAL` — is reached, which then drives the escrow's existing refund / reversal / release machinery. It depends on service-completion (Spec 20, ✅) which routes disputes into it, and on stripe-escrow (Spec 9, ✅) which owns all money movement. It references (never copies) checklist-photos (Spec 19), video-verification (Spec 18), and service-tracking (Spec 17) for evidence.

**It owns the dispute case + its resolution; it never moves money.** Spec 9 remains the source of truth for money (`setDisputeStatus`, `RefundService.refund`, `EscrowReleaseService.release`, `decideRefund`, ceilings, idempotency). `dispute-system` only chooses a resolution and **durably enqueues** the financial action Spec 9 executes. It holds no Stripe keys and makes no Stripe calls.

This plan is bottom-up and builds incrementally, mirroring the sibling specs (service-completion, stripe-escrow): config/constants + fail-fast `validateDisputeConfig()` + the schema migration (`disputes`, `dispute_evidence`, `dispute_escrow_intents` + `dispute_financial_intents` both with `dispute_id ON DELETE SET NULL`, `dispute_object_deletions` + its tombstone trigger, `dispute_outbox`, all constraints/indexes/CHECKs from the design's Data Models) → entities + types/enums (incl. `ACTION_BLOCKED`, `EscrowActionResult`, `NO_OP`) → the pure policy files (initiation policy, resolution-mapping) → the `EscrowClient` seam (the ONLY bridge to Spec 9, honoring contracts (a) atomic block-vs-release, (b) accepted `NO_OP`, (c) reject-second-effect `PAYMENT_ALREADY_SETTLED`) → repositories (single-winner writes co-writing intents + outbox in one tx, lease-based intent drain/claim keyed off `payment_id`) → the storage service (grant-gated MinIO uploads, inspect, tombstone-safe delete) → the upstream-evidence reader → participation + creation services (idempotent `createFromRouting`, phase derived from Spec 9's `payout_status`) → lifecycle + resolution + SLA services (single-winner, clear-escrow-LAST) → evidence service → the `service_disputed` consumer (its own `consumer_name='dispute'` checkpoint) → jobs (escrow-intent worker, financial-intent worker with `BLOCKED → ACTION_BLOCKED` handling, SLA sweep, retention/tombstone/stale-grant cleanup) → controller + DTOs + module wiring (`validateDisputeConfig()` on boot) → checkpoint (backend) → mobile core (types, api, store, `useResolutionCountdown` from the durable deadline) → mobile screens + i18n → checkpoint (mobile) → property-based (P1–P15), unit, DDL, integration, and mobile tests → docs. Everything is testable in CI (backend) and locally (mobile), with Spec 9 (`EscrowClient`), MinIO, BullMQ, and Postgres as mocked seams — zero real external calls, no Stripe SDK imported anywhere in the module.

Scope: one **active** dispute per completion (partial-unique over `state IN ('OPEN','UNDER_REVIEW')`); the dispute CASE + resolution (never the money ledger); phase from Spec 9's authoritative payment state; single-winner transitions; durable escrow-block + financial-action intents that survive the case via `ON DELETE SET NULL`; clear-escrow-LAST; never stuck (SLA fallback). See `requirements.md` (Req 1–7 + REQ-DS1…REQ-DS12) and `design.md` (Properties P1–P15).

## Notes

- Tasks marked with `*` are optional (tests) and can be skipped for a faster MVP — but per this project's execution rules they are executed (unit, property-based, DDL, integration, mobile).
- Each task references specific requirements; property/integration tests cite the design's P1–P15 and the requirements' REQ-DS1…REQ-DS12.
- **Authority split (strict).** PostgreSQL is the source of truth for the dispute CASE + resolution; the escrow module (Spec 9) is the source of truth for money; checklist-photos (Spec 19), video-verification (Spec 18), service-tracking (Spec 17) are authoritative for the evidence they recorded; `dispute-system` references them, never mutates. `dispute-system` owns the WHEN/decision, never the HOW of money — it holds no Stripe keys and imports no Stripe SDK.
- **Durable-event init:** the dispute is created by consuming the `service_disputed` outbox fact via a `consumer_name='dispute'` checkpoint over Spec 20's `completion_outbox` fan-out — never a synchronous call and never a mobile `POST /disputes`. A creation failure never rolls back the completion routing. The mobile "open dispute" UX drives Spec 20's completion flow; Spec 20 owns the trigger.
- **Phase from one explicit Spec 9 field.** `phase` is `POST_RELEASE` iff Spec 9 `payout_status IN ('TRANSFER_CREATED','PAID')`, else `PRE_RELEASE` — derived at creation via `EscrowClient.readPaymentPhase`, snapshotted, never inferred from the completion's `CONFIRMED`/`AUTO_RELEASED` and never from a mixed accepted/executed notion.
- **Durable intents + lease reclaim, applied twice.** Opening commits an `OPEN` `dispute_escrow_intent` in the same tx as the dispute; resolving/expiring commits exactly one `dispute_financial_intent` in the same tx as the terminal transition. Separate workers drain each into Spec 9 with idempotent retries, claiming via a single-winner lease; a `DISPATCHED` intent orphaned by a crash is re-claimable once its `lease_until` passes.
- **Clear-escrow-LAST.** `disputeStatus` stays `OPEN` until Spec 9 has durably *applied* the resolution's financial action (`APPLIED`/`CEILING_CLAMPED`/accepted `NO_OP`); only then is a `NONE` escrow-block intent enqueued. A `BLOCKED` outcome → the financial intent moves to the durable `ACTION_BLOCKED` needs-review terminal, the `NONE` clear is NOT enqueued, `disputeStatus` stays `OPEN`, and the case is surfaced for operator review — money-not-moved never leaves the escrow unblocked.
- **Intents survive the case (blocker 2).** `dispute_escrow_intents.dispute_id` and `dispute_financial_intents.dispute_id` are `ON DELETE SET NULL` (not `CASCADE`), with `payment_id NOT NULL`: a money command is never destroyed before it lands. Both workers key off `payment_id` + the intent row, so they complete even when `dispute_id` is nulled by a cascade. Evidence and the dispute row still cascade from the parent completion/offer.
- **Single-winner everywhere terminal.** `OPEN → UNDER_REVIEW`, `{OPEN|UNDER_REVIEW} → RESOLVED`, and `{OPEN|UNDER_REVIEW} → EXPIRED` are conditional writes (`WHERE state=:expected`); the winner co-persists derived fields + exactly one financial intent + the outbox in one tx. Resolve-racing-SLA resolves to exactly one terminal, never two financial intents.
- **Ceilings owned by Spec 9.** `dispute-system` chooses favor-Cleaner/Host/partial + the requested amount; Spec 9 computes the exact refund/proportional-reversal amounts + ceilings, surfaced back as `effective_amount_cents`. `resolution_refund_cents` is the requested amount only and never overrides Spec 9.
- **At most one financial effect per payment (blocker 4, P15).** Once a payment has a durably applied dispute-driven effect, Spec 9 rejects any further one with `BLOCKED` (`PAYMENT_ALREADY_SETTLED`); a second dispute may open but its intent surfaces `BLOCKED → ACTION_BLOCKED` and produces no second refund/release. The guard lives in Spec 9, not merely the per-dispute unique.
- **Never stuck.** An unresolved dispute past its snapshotted `resolution_deadline` converges to `EXPIRED` with the configured `DISPUTE_FALLBACK_RESOLUTION` + its financial intent (never `resolution=NULL`/intent-less), which clears the escrow after Spec 9 accepts it.
- **Evidence referenced + gated.** Upstream facts are typed references (never byte copies), resolved on read to short-lived participant/resolver-gated pre-signed URLs (visual) or gated structured data (structured — never a URL). Host/Cleaner photos use the grant-gated MinIO upload pattern (grant persisted before the pre-signed PUT, finalize re-checks + server-inspects). A `HOST_PHOTO` object is tombstoned on delete/cascade and hard-deleted only for a TERMINAL dispute past the retention floor.
- **`GET` reconciliation is authority; realtime is advisory.** Dispute state + intents + `GET /disputes/:id` (no internal intent fields exposed) are authoritative; a missed push never changes a resolution or its money effect. The mobile countdown is a display of the durable server deadline.
- **No hardcoded config/secrets.** Windows, reason codes, fallback policy, buckets, limits, lease, retention floor come from config with fail-fast `validateDisputeConfig()` (incl. `DISPUTE_INTENT_LEASE_MS > DISPUTE_INTENT_DRAIN_INTERVAL_MS` and `DISPUTE_EVIDENCE_RETENTION_DAYS >= window + SLA + audit buffer`). MinIO creds never reach the client except as time-boxed pre-signed URLs; no payment secrets/PII in logs or outbox payloads (ids/enums only); reason text validated/escaped.
- **Out of scope:** moving money / calling Stripe / recomputing commission/ceilings / reimplementing refund/reversal/release (Spec 9); ML evidence-scoring / an AI judge (v1 uses rule-assisted operator resolution and/or a deterministic policy); a new escrow-blocking mechanism (reuses Spec 9's `disputeStatus = OPEN`); re-deriving/mutating the checklist/verification/payment ledger; public evidence exposure; a client-authoritative countdown; push delivery (Spec 16); any change to the escrow/completion/checklist/verification/offer contracts beyond creating the dispute from routing, setting `disputeStatus`, referencing evidence, and enqueuing the resolution's financial action.
- CI: backend jobs (API lint/typecheck, API tests) must stay green; mobile is verified locally (`tsc --noEmit` + ESLint + Jest).
