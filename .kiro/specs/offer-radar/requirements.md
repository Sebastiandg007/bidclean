# Requirements

## Overview

The Offer Radar is the Cleaner's primary screen — a full-screen interactive map showing real-time cleaning offers published by Hosts within their operating radius. Cleaners see animated pins representing available offers, can filter by criteria, and tap to view details before deciding to accept or counteroffer. The radar receives new offers in real-time via Centrifugo WebSocket (personal channel `offers:cleaner:{cleanerId}`) and provides a list view as an alternative to the map. The screen is the entry point for the entire Cleaner marketplace experience.

### Architectural Principles

- **REST is the source of truth.** WebSocket (Centrifugo) is a real-time transport layer for incremental updates. If conflict exists between cached WebSocket data and REST response, REST wins.
- **Backend enforces all eligibility rules.** Mobile never decides offer visibility based on KYC, role, subscription, or availability — it trusts the API response.
- **Privacy by design.** Exact property coordinates never reach the client. The backend provides a stable `public_location` (snapped/jittered point) per offer.
- **Work zone defines discovery, GPS defines UX.** The Cleaner's configured work zone center + radius determines which offers are delivered. GPS is used only for map centering and distance display.

## Functional Requirements

### 1. Map Display

1.1. The radar SHALL render a full-screen Mapbox map using the BidClean dark custom style as the default.

1.2. The map SHALL center on the Cleaner's current GPS location on first load.

1.3. The map SHALL display the Cleaner's position with a distinct animated marker (pulsing ring indicating "live" status).

1.4. The map SHALL display a semi-transparent radius circle around the Cleaner's position representing their configured work zone radius (from `cleaner_profiles.work_radius_meters`).

1.5. The map SHALL support standard gestures: pinch-to-zoom, pan, rotate, and double-tap-to-zoom.

1.6. The map SHALL use Mapbox native symbol layers with clustering (NOT React Native `<Marker />` components) — this ensures 60fps rendering with 200+ offers.

1.7. Tapping a cluster SHALL zoom the map to show individual pins within that cluster.

1.8. The map style SHALL support both dark mode (default) and light mode based on the user's theme preference.

### 2. Offer Pins

2.1. Each available offer SHALL appear as an animated pin on the map at the offer's `public_location` — a stable city-level approximate point generated by the backend at publish time and snapshotted on the offer (NOT derived from exact property coordinates on each request).

2.2. Pins SHALL use a spring animation on appearance (drop + bounce effect via Reanimated 3).

2.3. Pins SHALL visually differentiate by service type using distinct icon shapes or colors defined in constants.

2.4. Pins SHALL display the offered price (Cleaner payout after commission) as a label badge on or near the pin.

2.5. Pins SHALL visually indicate urgency level: offers scheduled within 2 hours show a pulsing/glowing effect.

2.6. When a pin's offer state changes to CANCELLED, EXPIRED, or MATCHED, the pin SHALL animate out (fade + scale down) and be removed from the map.

2.7. New offer pins SHALL appear with an entrance animation and optional haptic feedback (configurable).

2.8. Pins for offers already viewed by the Cleaner SHALL have a subtle visual distinction (reduced opacity or dot indicator).

### 3. Real-Time Offer Reception

3.1. The radar SHALL subscribe to the Cleaner's personal Centrifugo channel (`offers:cleaner:{cleanerId}`) on screen mount.

3.2. When a new offer delivery event (`offer_new`) arrives via WebSocket, the corresponding pin SHALL appear on the map within 1 second.

3.3. When an offer status change event (`offer_status_changed`) arrives with state `CANCELLED`, `EXPIRED`, or `MATCHED`, the corresponding pin SHALL be removed with exit animation.

3.4. The WebSocket event schema for status changes SHALL be:
```json
{
  "type": "offer_status_changed",
  "offerId": "uuid",
  "state": "CANCELLED | EXPIRED | MATCHED",
  "changedAt": "ISO 8601 timestamp"
}
```
This is extensible — future states can be added without creating new event types.

3.5. If the WebSocket connection drops, the radar SHALL display a subtle connectivity indicator and attempt automatic reconnection with exponential backoff.

3.6. On reconnection, the radar SHALL fetch the current list of available offers via REST API to reconcile state (REST wins over any stale WebSocket data).

3.7. The radar SHALL NOT display offers that have already been matched, expired, or cancelled — even if received briefly before the status update arrives.

### 4. REST API — Available Offers Endpoint (Cleaner View)

4.1. The API SHALL expose `GET /offers/available` — returns offers visible to the authenticated Cleaner based on the formal visibility contract (see 4.8).

4.2. The endpoint SHALL return paginated results sorted by distance (nearest first) as the default sort.

4.3. The endpoint SHALL accept **server-side** filter query parameters: `serviceType`, `minPriceCents`, `maxPriceCents`, `maxDistanceMeters`, `scheduledBefore`, `scheduledAfter`.

4.4. The response payload for each offer SHALL include: `offerId`, `propertySnapshot` (name, type, city, coverPhotoUrl), `serviceType`, `description`, `scheduledAt`, `timezone`, `estimatedDurationMinutes`, `priceBreakdown` (offeredPriceCents, commissionCents, payoutCents, currency), `distanceMeters`, `publishedAt`, `isUrgent` (boolean), `publicLocation` (lat, lng — approximate, stable per offer).

4.5. The endpoint SHALL NEVER return exact property coordinates, street address, or postal code — only city-level information and the `publicLocation` point (consistent with property privacy model).

4.6. The `publicLocation` field SHALL be a stable approximate point snapshotted on the offer at publish time. It SHALL NOT change between requests, SHALL NOT reveal the exact property address, and SHALL NOT be recalculated from the property if the property is later edited.

4.7. The endpoint SHALL support sort options: `distance_asc` (default), `price_desc`, `scheduled_asc`, `published_desc`.

4.8. **Formal visibility contract** — An offer is visible to a Cleaner if and only if ALL of the following are true:
  - `offer.state = 'ACTIVE'`
  - `offer_deliveries.cleaner_id = authenticatedCleanerId`
  - `offer_deliveries.delivery_status = 'SENT'`
  - The offer has not expired (server-side check)
  - The Cleaner's access has not been revoked

  Where `delivery_status = 'SENT'` means: the delivery transport (Centrifugo or OneSignal) successfully accepted the message for delivery. It does NOT mean the Cleaner opened, viewed, or acknowledged the offer.

4.9. All eligibility checks (KYC status, role, subscription tier, work zone, availability) are enforced by the backend at discovery/delivery time. The `/offers/available` endpoint trusts the `offer_deliveries` table as the authoritative record of what was delivered — it does NOT re-evaluate eligibility on every request.

### 5. Filters

5.1. The radar SHALL provide a filter panel (bottom sheet or collapsible header) with the following filters:
  - Service type (multi-select chips: standard, deep, move_in_out, post_construction, post_event, recurring)
  - Price range (min/max slider, in local currency display)
  - Maximum distance (slider with km display)
  - Scheduled date range (date picker: today, tomorrow, this week, custom)

5.2. Active filters SHALL be indicated visually (badge count on filter button, highlighted chips).

5.3. Filters SHALL be applied server-side via query parameters on `GET /offers/available`. The map and list view both reflect the server response.

5.4. Filter values SHALL persist during the session (Zustand store) but reset between app launches.

5.5. Clearing all filters SHALL be possible with a single "Clear all" action.

5.6. Client-side-only filters (not sent to API): view mode toggle, "already viewed" indicator. All other filters are server-side to avoid transporting unnecessary data.

### 6. List View (Alternative to Map)

6.1. The radar screen SHALL offer a toggle between Map view and List view (segmented control or swipe gesture).

6.2. The list view SHALL display offer cards sorted by the selected sort option (default: distance ascending).

6.3. Each offer card SHALL show: property cover photo (thumbnail), property name, property type, service type badge, price (Cleaner payout), distance, scheduled date/time, urgency indicator if applicable.

6.4. The list SHALL support pull-to-refresh to re-fetch available offers.

6.5. The list SHALL support infinite scroll pagination (load more on scroll to bottom).

6.6. Tapping a card SHALL navigate to the Offer Detail screen.

6.7. Every 5th card position in the list SHALL be reserved for an ad slot for free-tier Cleaners. Ad visibility is controlled by an `adsEnabled` flag derived from the entitlement layer (not by checking `cleaner_pro` directly in the Radar component). This abstraction allows entitlement names to change without modifying Radar code.

### 7. Offer Detail Preview (Bottom Sheet)

7.1. Tapping a pin on the map SHALL open a bottom sheet with an offer summary preview (not full-screen navigation).

7.2. The bottom sheet SHALL show: property name, type, city, cover photo, service type, scheduled date/time, duration, Cleaner payout amount, distance.

7.3. The bottom sheet SHALL have a "View Full Details" button that navigates to the full Offer Detail screen.

7.4. The bottom sheet SHALL have a "Quick Accept" button that delegates to `offer-negotiation` module. Quick Accept is a UX shortcut — the actual acceptance logic (server revalidation of offer state, Cleaner eligibility, expiration, match status) is entirely handled by `offer-negotiation`.

7.5. The "Quick Accept" button SHALL be disabled when the device is offline (backend cannot validate acceptance).

7.6. Swiping down on the bottom sheet SHALL dismiss it and return focus to the map.

### 8. Empty State & Radius Expansion Suggestion

8.1. When no offers are available within the Cleaner's work zone, the radar SHALL display an empty state with a friendly illustration and message.

8.2. The empty state SHALL suggest expanding the work zone radius with a CTA button that navigates to the Cleaner's work zone settings (in profile).

8.3. When offers exist but all are filtered out, a different message SHALL indicate "No offers match your filters" with a "Clear filters" CTA.

### 9. Location & Permissions

9.1. The radar SHALL request location permission on first access with a clear explanation of why location is needed (i18n text).

9.2. If location permission is denied, the radar SHALL show a fallback state explaining that location is required for the radar to work, with a button to open device settings.

9.3. The Cleaner's GPS location SHALL be used ONLY for: (a) centering the map, (b) calculating display distance to offers, (c) showing their position marker. It SHALL NOT be used to determine offer eligibility (that's work zone based).

9.4. Location updates SHALL respect battery optimization — use significant-change monitoring when app is backgrounded, high-accuracy when foregrounded.

9.5. The Cleaner's GPS location SHALL NOT be persisted indefinitely by the backend. Only the minimum location state required for map display may be retained in memory. No historical GPS tracking data is stored.

### 10. Work Zone vs GPS — Discovery Semantics

10.1. Offer discovery and delivery (which offers a Cleaner receives) is based on the Cleaner's **configured work zone** (center point + radius stored in `cleaner_profiles`), NOT their live GPS position.

10.2. Changing GPS position (e.g., driving to another part of the city) SHALL NOT cause offers to appear or disappear from the radar. The universe of available offers is stable as long as the work zone configuration doesn't change.

10.3. The Cleaner's GPS is used for **display purposes only**: map centering, distance labels, position marker. It never influences which offers are delivered or visible.

10.4. If the Cleaner wants to see offers in a different area, they must update their work zone settings — not simply move their device.

### 11. Availability & Eligibility

11.1. If the Cleaner changes their availability status to "unavailable" while offers are displayed on the radar, existing pins SHALL remain visible (they were already delivered). No new offers will be delivered while unavailable (enforced by `CleanerDiscoveryService` on the backend).

11.2. Radar availability display is advisory — final Cleaner eligibility is revalidated by `offer-negotiation` at acceptance time. The Radar does NOT prevent viewing offers based on availability status.

11.3. Backend eligibility checks (KYC, role, subscription tier, work zone, availability) are applied at **delivery time** by `CleanerDiscoveryService`. The Radar trusts the delivery records and does not re-implement these checks client-side.

### 12. Performance & UX

12.1. The initial map render with pins SHALL complete within 2 seconds on mid-range devices.

12.2. Adding a new pin (real-time delivery) SHALL animate within 300ms of event reception.

12.3. The map SHALL render smoothly at 60fps during pan/zoom gestures even with 200+ pins visible (achieved via native Mapbox symbol layers, NOT React Native Marker components).

12.4. Pin interactions (tap → bottom sheet) SHALL respond within 200ms (haptic + visual feedback).

12.5. Skeleton loaders SHALL appear during initial data fetch (never a generic spinner).

12.6. The radar SHALL pre-load offer data so that navigating to the detail screen is instant (data already in Zustand store).

### 13. Offline & Error Handling

13.1. If the device loses internet connectivity, the radar SHALL display existing cached pins with a banner indicating "Offline — data may be outdated" and mark all cached offers as `stale = true`.

13.2. Stale/cached offers SHALL be visually distinguishable (e.g., reduced opacity) to indicate they may no longer be available.

13.3. While offline, the "Quick Accept" button SHALL be disabled (acceptance requires server validation).

13.4. When connectivity returns, the radar SHALL automatically refresh (fetch available offers via REST + reconnect WebSocket). REST response replaces all cached data (REST wins).

13.5. API errors SHALL be shown as non-blocking toast notifications, not full-screen error states.

13.6. If the Centrifugo connection fails persistently (3+ reconnection attempts), the radar SHALL fall back to periodic REST polling (configurable interval) until WebSocket recovers.

### 14. Reconciliation Semantics

14.1. **Initial load:** REST fetch → populate map + list (source of truth).

14.2. **Real-time updates:** WebSocket events → incremental additions/removals (transport layer).

14.3. **Reconnection:** REST fetch → full reconciliation. All current pins are replaced by REST response. Any pin present locally but absent from REST is removed. Any offer in REST but not on map is added.

14.4. **Conflict resolution:** If WebSocket says an offer exists but REST says it doesn't → remove it (REST wins). If REST says an offer exists but WebSocket sent a cancellation → remove it (later event wins within same session, but next REST fetch is definitive).

## Non-Functional Requirements

### Performance
- Map + 200 pins renders in < 2 seconds on Galaxy A14 (baseline device) using native Mapbox layers
- WebSocket event → pin animation < 1 second end-to-end
- REST API `/offers/available` responds in < 300ms (p95) with server-side filtering
- Memory usage of radar screen < 150MB (including map tiles)

### Accessibility
- Offer pins have accessible labels for screen readers (price + service type + distance)
- List view is fully navigable with VoiceOver / TalkBack
- Filter controls meet WCAG 2.1 AA contrast ratios
- Map interactions have non-map alternatives (list view)

### Security
- Exact property coordinates are NEVER sent to the client — only `publicLocation` (stable approximate point, snapshotted per offer)
- Cleaner GPS location is never shared with other Cleaners
- Cleaner GPS location is NOT persisted as historical tracking data
- WebSocket channel is authenticated (Centrifugo JWT token)
- Offer data only shows what the Cleaner is entitled to see (no private Host data)

### Scalability
- Radar handles 200+ concurrent offers on map without frame drops (native Mapbox clustering)
- WebSocket maintains connection for sessions > 30 minutes without timeout
- REST endpoint handles 1000+ concurrent Cleaner requests (server-side filtering + pagination + proper indexing)

### Internationalization
- All UI text uses i18n keys (no hardcoded strings)
- Price displays respect locale currency formatting (COP, USD, CAD, EUR, GBP)
- Distance displays in km (metric countries) or miles (US, UK) based on user locale
- Date/time displayed in Cleaner's local timezone

## Dependencies

- **Spec 5 (property-management):** Property data model, PostGIS location, property public view
- **Spec 6 (offer-publishing):** Offer data model, state machine, Centrifugo delivery channels, `offer_deliveries` table, `CleanerDiscoveryService` interface, commission calculation, `offer_status_changed` event
- **Spec 4 (user-profile):** Cleaner work zone (center + radius) configuration
- **Centrifugo:** WebSocket transport for real-time offer delivery (already configured in offer-publishing)
- **Mapbox SDK:** `@rnmapbox/maps` for React Native map rendering (native symbol layers)
- **Reanimated 3:** Pin animations, transitions
- **Zustand:** Radar state management (offers, filters, view mode)
- **RevenueCat SDK:** Entitlement check for ad-free experience (abstracted via `adsEnabled` flag)

## Out of Scope

- Accepting or counteroffering an offer (handled by `offer-negotiation` spec)
- Push notifications for new offers (already handled by `offer-publishing` via OneSignal)
- Cleaner favorites management
- Service tracking after acceptance
- Payment/escrow flows
- Chat between Host and Cleaner
- Cleaner availability toggle UI (handled by profile/settings)
- Work zone configuration UI (handled by profile/settings)
